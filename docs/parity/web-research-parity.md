# Composer controls and web research: what reaches the backend

Audit for release 1.87.0. Read from code, not from changelogs. "Sent" means it is in a request body;
"local" means it changes only what this machine does.

## 1. How each composer control reaches the backend

| Control                                    | Editor path (Runtime V2 agent run)                                                                                                                                                                                                                                          | Editor path (legacy chat, compare, agent workflows)                                                         | Headless / SDK before 1.87.0                                | Headless / SDK now                                                                                                               |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Run: Agent, Chat, Compare, Compare + Judge | Agent only. `runQueuedAgent` starts a run with the prompt, thread, provider, model and attached file ids.                                                                                                                                                                   | Chat sends a `MessageRequest`; Compare sends a `CompareRequest` (`models`, `judgeEnabled`, `judgeModel`).   | Agent only.                                                 | Agent only, by design: Chat and Compare are editor surfaces.                                                                     |
| Effort                                     | `effortMode` becomes `effortBudget(mode)`, the run `budget` of the start request (seven fields), and is recorded in the journal and trace. **Sent, as numbers.**                                                                                                            | Not sent: `MessageRequest` has no budget field.                                                             | Only `--budget default\|long` and `--max-turns`. No effort. | `--effort` / `effort`: the same `effortBudget` table, sent as the run budget.                                                    |
| Agent (Auto / Plan)                        | `agentMode` is written into the run prompt by `composePrompt` and stored in the journal. **Sent, inside the prompt text.** Legacy `decidePermission` also refuses edits and commands in Plan.                                                                               | Same prompt prefix.                                                                                         | `--permission-mode plan` (read and git only).               | Unchanged. Plan is a permission mode.                                                                                            |
| Speed                                      | **Local.** `readConcurrency(speedMode)` sets how many containment checks and stats run at once while workspace context is read (1, 4 or 8). Fast mode pairs 2X with `LOW_LATENCY` routing, and the routing half is sent.                                                    | Same.                                                                                                       | Nothing.                                                    | `--speed` / `speed`: same function, same widths.                                                                                 |
| Approval                                   | **Local.** `permissionMode` goes to the policy adapter (`policy-v2`), is clamped by the organization ceiling, and is hashed into the journal's policy snapshot. The backend is never told.                                                                                  | Legacy `decidePermission` for edit proposals.                                                               | `plan`, `ask`, `accept-edits`.                              | Adds `autonomous-scoped` and `strict`, from the same `policy-v2`.                                                                |
| Context                                    | **Local, and not in the V2 run start.** The start request carries the prompt and file ids; I found no call that feeds `contextMode` into it. The agent reads files through tools.                                                                                           | Collected by `WorkspaceContextService`, wrapped by `assembleContextEnvelope`, sent inside the message text. | Nothing.                                                    | `--context-mode` and friends: the same `collectContext` and envelope, sent inside the prompt text.                               |
| Web research                               | **Dropped on V2.** `runQueuedAgent` sees a non-`NONE` research mode and switches the whole run to the legacy payload (`requiresLegacyPayload`), so research costs the run its V2 path. The V2 tool `workspace.web` (search, fetch) is registered regardless of the control. | Sent: `researchMode` on the message and compare requests. The chat service runs the research.               | Nothing; no web tool.                                       | `--research` / `research` decides which `workspace.web` operations are offered. Not sent: the run request has no research field. |

Silently dropped, in short: research mode on the V2 run start; effort, context and speed on the legacy chat request; nothing on the
approval control is ever sent, by design.

The run request the headless runner builds (`HeadlessRunRequest`) still has no effort, speed, research or context field. 1.87.0 does
not invent one: effort is carried by the budget numbers it already has, and the rest is local.

## 3. What the extension lacked, and what 1.87.0 closes

The V2 `workspace.web` tool had `search` and `fetch`, and its `fetch` threw away the page's `links`.

| Gap                                                                                      | Status in 1.87.0                  | How                                                                                                                                                                                                                                                                                |
| ---------------------------------------------------------------------------------------- | --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Crawl a site                                                                             | **Closed, client side, bounded.** | `crawl` follows `links` from `/research/fetch` breadth first: same host only, at most 30 pages, depth 3, one page at a time, 120 000 characters in all and 12 000 per page.                                                                                                        |
| Link and page structure                                                                  | **Closed.**                       | `extract` returns the final address, content type, size, cache hit, and links split into same-site and other-site.                                                                                                                                                                 |
| Safe URL handling for the new operations                                                 | Kept.                             | Every start URL and every followed link passes `assertFetchableUrl` (http and https only, no credentials, no private or link-local address). The address that answered is checked again.                                                                                           |
| Truthfulness                                                                             | Kept.                             | A page that was refused, answered HTTP 4xx, redirected off the host, redirected to a private address or failed is listed in `skipped` with a redacted reason. A redirect within the host is flagged `redirected`. `stoppedBy` says why the crawl ended. All output is `untrusted`. |
| Fetch timeout limit                                                                      | **Fixed.**                        | The client accepted up to 120 000 ms; the service rejects above 60 000. Now 60 000.                                                                                                                                                                                                |
| Headless web tool                                                                        | **Added.**                        | `--research` and the SDK `research` offer `workspace.web` from the command line, through the same code (`core/web-research-operations`).                                                                                                                                           |
| Sitemap and feed discovery, ranking links by the question, 200 pages in parallel         | **Needs a backend change.**       | See below.                                                                                                                                                                                                                                                                         |
| Extraction profiles (`ARTICLE`, `DOCS`, `TABLE`), fetch and extract, repository analysis | **Needs a backend change.**       | See below.                                                                                                                                                                                                                                                                         |
| Research on a V2 run, the plan, the self-crawl and the narrated log                      | **Needs a backend change.**       | See below.                                                                                                                                                                                                                                                                         |
| A "crawl" option in the composer                                                         | **Not added.**                    | There is no backend research mode for it: the web app derives a crawl from the wording of the message. Adding a composer value the server would ignore would be a fake control.                                                                                                    |

### The exact backend change that would close the rest

1. **A user-permission research workflow route.** In `apps/claw-research-service`, add `POST /research/workflows`
   (`@RequirePermissions(Permission.RESEARCH_USE)`) that accepts the existing `executeResearchSchema` but only for
   `SITE_CRAWL` and `SEARCH_FETCH_EXTRACT`, and calls `ResearchManager.run`. Keep `REPO_CLONE_ANALYZE` and the run history on
   `ADMIN_SYSTEM_VIEW`. Apply the same plan check for research access the chat service applies. This gives the extension sitemap and
   feed discovery, ranking, parallel crawling to 200 pages and the extraction profiles with no client-side guessing.
2. **A research field on the Runtime V2 run start.** In `claw-chat-service`, accept an optional `researchMode`
   (`SEARCH`, `SEARCH_FETCH`, `SEARCH_EXTRACT`) on `POST /chat-messages/runtime/runs`, run it through the existing research gate and
   narration, and stream the work log as runtime events. Then the extension would stop abandoning the V2 path when research is on, and
   `--research` could be sent as well as used locally.
3. **Optional:** make `GET /research/fetch-strategies` readable with `RESEARCH_USE`, or have `/research/fetch` report which strategy
   it used, so a client can tell a browser-rendered page from a plain one.

Until then the client-side crawl is an approximation: it cannot read sitemaps (the fetch route returns cleaned text, not XML), cannot
rank links by the question, and is slower than the server crawler. It says so in the tool description only as far as it is true:
it reports what it read and what it skipped.

## 4. What the backend ignores, stated once

- No composer control except effort (as the budget numbers) and research (on the legacy chat request) is sent to the server.
- In a headless run nothing is sent for speed, context, approval or research. They change the local read, the prompt text, what a
  tool call is allowed to do, and which tools are offered.
- The server's robots.txt and fetch-policy decisions are not repeated on the client. They arrive as refusals, and are recorded as such.

## 5. Not verified live

The new `crawl` and `extract` operations are covered by unit tests against a scripted site and a stubbed research route. They were
not run against a live ClawAI backend in this release, and the V2 tool catalog sent to the server now lists two more operations for
`workspace.web`. If the server validates operation names against a fixed list, the catalog would be refused; a live round on the next
deployment is the check.
